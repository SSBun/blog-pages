The Best Dependency Injection Framework

SSBun
2023-01-05 (Updated: 2023-01-05)
Architecture, Dependency Injection, iOS

在之前的分享中我们了解了依赖注入的各种概念和它所依托的依赖反转的设计思想，也介绍了其与 ServiceLocator（服务定位）之前的区别，同时还引入了依赖容器的概念，并在 ZXTModuleWallet 中付诸实现，最近在公考 AI 课程的开发中再试修改这个组件时，感觉依赖注入确实能将各个功能模块进行细致的拆分和隔离，需要修改的业务功能由各个依赖解耦和分隔

做为一个由来已久的概念，依赖注入在服务端已经应用的非常的广泛了, 我们平时也会在 API 设计中利用到依赖注入的思想, 其会增加一定的编码难度，所以基本上只在高复用低耦合要求较高的场景中使用了。
而随着业务的扩大，我们的独立 App 越来越多，对各个功能的复用需求也越来越多，这要求我们在设计代码时要尽量将功能拆分为更小的模块，然后再组合为一个业务模块，这样的组合设计有利于我们细粒度的拆分，合并，下沉及替换指定功能。而依赖注入就完美的契合了我们的应用场景，

优化组件化开发中的编译速度

组件化开发的目的之一是可以优化编译速度，我们对单一组件的修改只会导致此组件和对它有依赖的相关组件的重新编译，其余的组件 Xcode 会使用已经编译过的缓存，因为他们的编译产物并没有修改。
但是工程中，错误复杂的依赖方式会导致这一优化失效，甚至进一步增加编译时间。如果上层组件对下层组件进行了具体类型的依赖，那下层组件的变动会导致几乎所有的依赖方重新编译，复杂的纵向依赖会使得某一组件的变动导致所有的上层依赖缓存失效，而解决这一问题的方法就是将上层组件对下层组件的直接依赖，改变为对其他组件 API 的横向依赖。这样的依赖关系可以保证单一组件实现的变动不会传到至其他的组件，这能够大幅降低编译时间，并使得组件实现间的依赖完全解耦，方便我们进行多平台差异化的构建。
